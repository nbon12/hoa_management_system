Codebase Context

HOAManagementCompany is an ASP.NET Core / .NET 9 backend with an Angular 17.3 frontend (neko-hoa/). It currently ships one working surface — a Homeowner self-service portal — and a stated intent to add a second one that has never been built.

  • No role system exists yet. Identity is wired via AddIdentityCore<ApplicationUser> (Program.cs), not AddIdentity — AddRoles<IdentityRole>() is never called. JWTs carry sub/email/propertyId/communityId/jti only, no role claim. Registration binds one user to exactly one property and hard-blocks a second claim on the same property (AuthService.cs).
  • Board intent already exists as unwired UI. portal-select.component.ts renders five portal cards — Resident, Board/Mgmt, Vendor, Closing, Attorney — but every card routes to the identical /login path today.
  • The spec-kit umbrella/sub-spec pattern already shipped once, successfully. 016-security-hardening is a no-implementation-detail umbrella spec containing six sub-specs, all of which were later promoted to their own numbered branches (017–022), governed by Constitution §12 (Spec Independence & Parallelism). Two are merged, four are spec-only as of this writing.
  • The backlog tool the user is missing already exists, unused. /speckit.taskstoissues is a real command in this repo, but a repo-wide search turns up zero uses of it — sub-spec status has instead been tracked in a hand-maintained Markdown table.
  • Board-relevant backend capability is uneven. Documents are already community-scoped (Budgets/Minutes/Financials categories); Violations are hard-scoped to a single property with no community-wide query; a CommunityExpense entity and a LedgerEntry.FundCode field exist but only CommunityExpense is actually read today (in the resident dashboard) — neither is aggregated at the community level.
  • Design-to-code tooling is installed but thin. Storybook is configured and has one proven mocked-service story pattern, but only 3 of 17 frontend components use it. styles.scss has 18 color design tokens and no spacing/radius/shadow scale; no shared/ or ui/ component directory exists anywhere in the frontend.
  • External research (high value): HOA board portals are a mature SaaS category (Vantaca, AppFolio, TownSq, Buildium, CINC, FRONTSTEPS) where in-platform ARC (architectural review) voting is the named competitive wedge, and where the strongest products share one backend across homeowner and board views rather than bolting a second portal on. "Big bang release" is a named industry anti-pattern; the countermeasure is partitioning a rollout into independently valuable slices — exactly what this repo's own spec-kit pattern already does.

1

Umbrella spec + capability sub-specs, sequenced like 016

Description

Structure the Board Portal exactly the way 016-security-hardening was structured: one umbrella spec with no implementation detail, split into capability sub-specs (role/access, documents view, ARC workflow, financial rollup, vendor triage), each promoted to its own numbered Spec Kit branch when work starts on it. Declare the role/access sub-spec as the one explicit hard dependency the rest wait on — everything else runs in parallel per Constitution §12. Then actually invoke /speckit.taskstoissues once each sub-spec has a tasks.md, so GitHub Issues becomes the live, dependency-ordered backlog instead of a hand-maintained status table.

Axis

work-decomposition-sequencing

Basis

directspecs/016-security-hardening/spec.md states the work is split into six independently plannable/testable/deliverable sub-specs with "no implementation detail"; specs/016-security-hardening/HANDOFF-2026-07-12.md and the actual branch list confirm all six were promoted to numbered branches 017–022, two merged so far. tasks.md documents one real hard dependency and one soft file-conflict sequencing note between sub-specs — proof this scales past pure independence-in-theory. A repo-wide search confirms /speckit.taskstoissues exists as a command but has never been invoked; status instead lives in a hand-written table. 4 independently-generated ideas across the ideation fleet converged on this same recommendation.

Rationale

This is not a process to adopt on faith — it is a pattern this exact team already ran to completion once, with the dependency and sequencing edge cases already worked out. Pairing it with taskstoissues answers the user's stated gap ("no good backlog other than maybe GitHub Issues") with a command invocation instead of a new tool.

Downsides

Sub-spec boundaries have to be chosen deliberately — 020's "signup-UI gap" (a cross-slice requirement nobody owned, discovered late and retrofitted) shows what happens when they aren't. Adopting taskstoissues as standard practice is also a process decision that outlives this one feature and should be agreed to as such, not started unilaterally.

Confidence: High Complexity: Medium
2

First shippable slice: real Board route + Documents view

Description

Make the very first PR turn the dormant "Board / Mgmt" portal-select card into a real, guarded route — additive, beside the existing Homeowner routes, touching nothing about how homeowners log in — and have it serve exactly one capability that needs zero new backend queries: a read-only board view of Documents (already scoped by communityId, already carrying Budgets/Minutes/Financials categories). This is the smallest possible unit that turns an aspirational UI stub into a real fork in the codebase everything else attaches to.

Axis

role-access-model / board-feature-surface

Basis

directportal-select.component.ts — all five portal cards, including "Board / Mgmt", route to the identical /login path today, confirmed by reading the routing binding directly. DocumentsEndpoint.cs already reads communityId (not propertyId) off the user's claims, unlike every other community-surface endpoint checked. 2 independently-generated ideas converged on shipping documents first.

Rationale

Verification found this pair individually "too obviously correct to debate" rather than a genuine fork — which is exactly why it belongs first: it's the low-controversy, low-risk slice that proves the role-gating and routing pattern end-to-end before anything harder (ARC, budgets) depends on it being right.

Downsides

It's deliberately small — on its own it doesn't answer what "Board member" means as an identity (see idea 3). Treat it as a proof-of-plumbing slice, not the whole role/access sub-spec.

Confidence: High Complexity: Small
3

Board identity as a new grant type, not a role flag

Description

Don't retrofit "Board member" onto the existing UserProperty claim — that table assumes one owner per property and its registration path enforces that with a real security check. Instead, give Board membership its own community-scoped grant path: an invite-based registration (not a property claim code) that links a user to a community rather than a single property, and a JWT variant that can carry a community-wide scope so board members don't have to "switch properties" to see community-wide data the way homeowners do. Two refinements worth deciding alongside this: whether board grants should carry an election-cycle expiry (so departed board members don't silently keep access), and whether the scope-switching mechanic already built for homeowners (SwitchPropertyAsync) can be generalized rather than duplicated.

Axis

role-access-model

Basis

directUserProperty.cs has exactly Id/UserId/PropertyId/LinkedAt — no role column, no expiry field. AuthService.cs contains the exact check (AnyAsync(up => up.PropertyId == claimCode.PropertyId)) that blocks any second claim on a property. JWT claims today are exactly sub/email/propertyId/communityId/jti — one scope per token — and SwitchPropertyAsync already re-mints tokens on a property switch, which is the precedent for generalizing to scope-switching. 4 independently-generated ideas converged on "don't overload UserProperty," with an internal fork between a cheaper role-column patch and a cleaner separate table.

Rationale

The property-claim uniqueness check is real, already-hardened security logic from the 016 security-hardening work — reusing it for a structurally different relationship (one board member, many properties) means either weakening that guarantee or building parallel plumbing anyway. Deciding the shape now is cheaper than discovering the conflict mid-implementation.

Downsides

A new grant entity is more schema and more auth surface than a role column would be — the cheaper column-based patch was raised independently by two other agents and is a legitimate lower-cost alternative if the team judges the property-claim invariant doesn't need protecting this carefully for a first version.

Confidence: High Complexity: Medium
4

Storybook as the mandatory design-to-code gate

Description

Require every new Board-portal component to land as a real Angular component plus a Storybook story — built against a mocked backing service, following the pattern already proven in the payments feature — before it's considered "done." This turns Storybook from underused infrastructure into the literal contract between what Claude Design produced and what shipped: a design isn't accepted until it exists as a reviewable, testable component in isolation, not a static frame a human eyeballs into existence.

Axis

design-to-code-handoff

Basis

directStorybook is configured (@storybook/angular, an Angular CLI builder) but exactly 3 of 17 frontend components have .stories.ts files, all under features/payments/. The existing pattern (one-time.stories.ts) mocks the backing service via Angular's moduleMetadata so the story "never hits the network" — a working template, just underused. 5 independently-generated ideas converged on this — the single strongest finding in the design-to-code-handoff axis, verified against the actual file counts.

Rationale

The repo already paid for the mechanism that solves this problem; it's just never been required as policy. Using it as the acceptance gate for new Board work turns "does this match the design" from a subjective eyeball comparison against a drifting mockup into a checkable PR requirement, and it closes 13 of 17 components' coverage gap incrementally as a side effect.

Downsides

This is a Definition-of-Done change, not a one-off — it adds a step to every future Board PR and should be agreed to as team policy, not assumed. Retrofitting stories onto components built without them later is more expensive than requiring it from the first PR, so the timing of adoption matters.

Confidence: High Complexity: Small–Medium
5

Token layer first, then a constrained Claude Design brief

Description

Before Claude Design touches a single Board screen, extract the missing spacing/radius/ shadow scale from the hardcoded values scattered through styles.scss into named tokens alongside the 18 color tokens that already exist. Then give Claude Design a real brief per sub-spec (one mini-brief for Documents, one for ARC, one for Budgets — not one giant all-screens mockup) that hands over the token set and existing component patterns as hard constraints, rather than letting it invent its own spacing scale that then has to be reconciled against the Homeowner portal by hand.

Axis

design-to-code-handoff

Basis

directstyles.scss has an actively-used :root block with 18 color tokens (oklch-based) — verified directly, correcting an earlier overcount of "~21" — but no spacing, radius, or shadow scale; those values are hardcoded per class (e.g. a literal border-radius on .card). No shared/, ui/, or design-system/ directory exists anywhere in the frontend, and no Figma or design-tooling packages appear in package.json. 4 independently-generated ideas converged on this gap.

Rationale

Handing a design tool a system with half its foundation missing means it either invents its own spacing scale (fighting the existing CSS) or every Board screen re-derives spacing by eyeballing existing components — the exact "garbage in, garbage out" handoff failure mode external research on 2026 design-handoff tooling flags as a production risk, not a cosmetic one. A few days of token work up front is cheaper than cleaning up drift across five sub-specs later.

Downsides

This is frontend-infrastructure spend that delays visible Board functionality in exchange for compounding leverage on every screen after — worth an explicit go/no-go rather than defaulting into it, and it should be scoped small (a handful of tokens, not a full design system) so it doesn't become its own multi-week detour.

Confidence: High Complexity: Small–Medium
6

ARC review workflow, after fixing the violations query gap

Description

Build Architectural Review Committee (ARC) approval as an extension of the existing Violation model rather than a new entity: extend ViolationStatus beyond Open/Closed to include approval states (e.g. pending, approved, denied) and add a reviewer/note field, scoped to the existing Architectural category. This needs one explicit prerequisite first: the violations query today is hard-scoped to a single property, while every other community-facing query (documents, announcements) is already scoped by community — that asymmetry has to close before a board-wide ARC queue can exist at all.

Axis

board-feature-surface

Basis

directViolationCategory already has an Architectural value; ViolationStatus is exactly {Open, Closed} with no reviewer/note field on Violation. The violations query is scoped by propertyId while the documents query is scoped by communityId in the same feature area — confirmed by reading both endpoints directly. 3 independently-generated ideas converged on the ARC extension; a fourth independently flagged the query-scope asymmetry as the prerequisite.

Rationale

External research names in-platform ARC voting as the clearest competitive wedge among comparable HOA products — the alternative today is scattered email/text. This is also the cheapest version of that feature to build here: the category taxonomy already exists, so it's extending an enum and adding fields, not designing a new subsystem from scratch.

Downsides

Widening the violations query to be community-scoped raises a real question the team should decide deliberately: does a board-wide view leak cross-property violation data to residents who shouldn't see it, and does the endpoint need a separate board-only path rather than a widened shared one?

Confidence: High Complexity: Medium
7

Board financial rollup from existing ledger & expense data

Description

Build a board budget-vs-actuals view by aggregating the existing per-property ledger data community-wide, activating the LedgerEntry.FundCode field that's never set today, and extending the CommunityExpense entity's use beyond its current read-only role in the resident dashboard into a real board-facing endpoint with community-level aggregation.

Axis

board-feature-surface

Basis

directLedgerEntry.FundCode exists as a GL hook but no code path ever sets it, confirmed by a repo-wide search. LedgerService's balance and recompute methods are scoped by propertyId only — no community-wide aggregate exists. CommunityExpense is community-scoped with Label/Amount/FiscalYear fields shaped like a budget line item, and — corrected during verification — it is not fully dormant: DashboardService.cs already reads it into the existing per-resident dashboard's expense-breakdown widget. What's missing is a cross-property/board-level aggregate and a dedicated board endpoint, not first-time usage. 5 raw ideas across the fleet independently found this schema — the single most corroborated finding of the whole run — though the strongest version overstated "CommunityExpense is unused."

Rationale

Even after the correction, this is real leverage: no new tables, mostly service/endpoint work over schema that was already designed for this purpose and partially wired. It's a meaningfully cheaper path to a board financial view than designing a budgeting feature from scratch.

Downsides

Because CommunityExpense is already live in the resident dashboard, changes here touch an existing, working read path — this needs care to avoid regressing that widget while extending it, not a clean-slate build.

Confidence: Medium Complexity: Medium
